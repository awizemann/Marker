## Description

Marker 0.9.0 dark mode, phase 1. Source of truth: ~/Developer/TrapperKeeper/design/TrapperKeeper_DarkMode_Handoff (APPEARANCE.md, DesignSystem/TKColor.swift, Prototype/TrapperKeeper Editor.dc.html token blocks). Goal: any MarkerTheme built from dynamic colors (TKColor.adaptive) re-resolves in the editor on appearance change, and Marker's own 6 accent defaults get dark values from the handoff's token families: highlightBackground dark = amber 233,187,114 @0.30; tableZebra dark = white @0.05 (line-rgb family); activeLineTint dark = 31,190,106 @0.08 (the prototype's source-reveal green lift); codeString dark #E5BB72 (dirty-fg); codeConstant dark #74CEE2 (cloud-fg); codeType dark #4BDA8D (deep). Light values unchanged.

## Plan

1. Add MarkerTheme.adaptive(light:dark:) (NSColor(name:nil,dynamicProvider:) → Color) so consumers without TKColor can build adaptive themes; use it for the 6 accent defaults (public init default args must stay public-expressible). 2. Audit every NSColor(theme.x) site (EditorStyling, CodeWellTextView, EditorView, TableGridView, FormatBar, CommandPaletteView, WikiCompletionController, TableSubstitution) — ensure no site snapshots a resolved color (e.g. via .cgColor / usingColorSpace) in a way that freezes appearance; any cache keyed by color must include appearance (CodeWellTextView.checkboxImageCache). 3. Empirical test in MarkerEditorTests: style a storage with an adaptive theme, resolve attribute colors under NSAppearance(named:.aqua) vs .darkAqua via NSAppearance.performAsCurrentDrawingAppearance, assert they differ and match the expected values. 4. swift build/test; fresh-eye audit.
